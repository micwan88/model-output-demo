TMD Emulator: story 1 (r1) report

Plan main-plan-1-r1.md · author: main (Claude) · 2026-09-20 · status: Completed

In one paragraph. A new TMDEmulator/ .NET 8 solution now exists with a full-screen, colored, arrow-key terminal program and an xUnit project. It shows the menu tree from the story, and one function is real: Export MZMK Initialization Key saves the hardcoded test key's public point as upper-case HEX in MZMK_Init_{FP8}{yyyyMMddHHmmss}.der. The other three functions are placeholders. Build is clean (0 warnings), 161 unit tests pass, 40/40 real-terminal smoke checks pass on the Linux build, and the exported values match openssl. One thing I could not do: run the Windows .exe (this machine is Linux).

1. Context and intuition

The real key exchange goes through a Thales TMD (a physical secure device). That is impractical for development, tests and training, so this program pretends to be one in a controlled environment only. Because of that, it is allowed to be less strict on security (the test private key is in source code, on purpose).

The story is the first sub-story: get the shell of the emulator right (project, terminal UI, menus, config, one export function) so later stories only have to add screens. That drove one design rule: a screen is a small class that draws into a canvas and reacts to keys; the host owns layout, the status bar and navigation. Adding a menu entry later means adding one class and one line in MenuDefinition.

How the export works

  1. The screen shows the curve (read from the key, currently secp256r1), the private scalar and the public point, all upper-case HEX.
  2. The path prompt is pre-filled with the current absolute directory and is editable (←/→, Home/End, Backspace, Delete).
  3. Enter validates the folder. Problems appear in red in the status bar and the prompt stays open.
  4. If the target file exists you get Overwrite it? Yes / No. No (or Esc) goes back to the path prompt and writes nothing.
  5. Saved: the file holds the public point HEX text (04 || X || Y, 130 chars), ASCII, no BOM, no newline. You return to the menu with a "Saved: <full path>" message.

The 8-character fingerprint in the file name is the first 8 hex chars of SHA-256 over the SPKI DER bytes. That is a different input from the file content (the raw point), exactly as the story words it.

  • The status frame has two wrapped message lines, not one. I noticed the "Saved: <full path>" text is about 94 characters and would have cut off the file name on an 80-column terminal.

5. What was skipped, and what I could not verify

  • Not run on Windows 11. I only have Linux here. The exe is built and structurally valid, but nobody has seen it draw on a Windows console. Please do the short manual check below.
  • Tests ran on the .NET 10 runtime against net8.0 binaries (roll-forward, as you approved). A real .NET 8 runtime was not available.
  • ConsoleTerminal and Program have no unit tests. They are thin wrappers over System.Console and need a real terminal; the smoke test covers them on Linux only.
  • Windows and unusual-terminal behaviours are untested: the fallbacks that map a curve OID/friendly name (Windows reports them differently), a code page without box-drawing characters, and very old consoles.
  • The published exe is self-contained (~67 MB), untrusted (unsigned) and not trimmed. There is no installer or CI pipeline (out of scope).
  • The project folder is not a git repository and I added no .gitignore. publish/, bin/ and obj/ are build output.
  • Out of scope by the story: real key storage, finalize/uninstall logic, View Keys content.

Manual check on Windows 11 (about 2 minutes)

  1. Run publish\win-x64\TMDEmulator.exe in Windows Terminal (and once in classic conhost). Menu appears with a grey highlight row and black text on a black background.
  2. ↑/↓ moves and wraps. Enter opens Remote MZMK Setup; Esc goes back.
  3. Open Export MZMK Initialization Key. The box-drawing characters and ↑/↓/←/→ in the legend render properly (if you see ?, tell me).
  4. Press Enter to save; check the new MZMK_Init_11D3BE29…der file holds 130 hex characters starting with 04.
  5. Type a folder that does not exist: a red message appears under the legend.
  6. Shrink and grow the window: the layout redraws; Ctrl+C exits and leaves the console clean.

6. How to build, test and run

# from the project root
cd TMDEmulator
dotnet build TMDEmulator.sln
dotnet test  TMDEmulator.sln                 # on this box first: export DOTNET_ROLL_FORWARD=LatestMajor
dotnet run --project src/TMDEmulator

# release exe (Windows 11), single self-contained file
dotnet publish src/TMDEmulator/TMDEmulator.csproj -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -o publish/win-x64

To change colors edit tmdemulator.json next to the exe, for example { "colors": { "background": "DarkBlue" } }. Valid names are the System.ConsoleColor names. Wrong values are shown in red at startup and the default is used.

8. Quiz: you must pass this (6 of 8) before treating the change as understood

1. What text does the saved MZMK_Init_….der file contain?

The .der extension is misleading by design (TMD-specific). Per your Q2 answer it is HEX text of the point. I applied that to the file too, and asked you to confirm.

2. What is the 8-character fingerprint in the file name computed from?

The fingerprint input (SPKI DER) is different from the file content (raw point). For the embedded key it is 11D3BE29; I confirmed it with openssl.

3. How does the program know the curve to display?

Your Q1 answer. Tests use a generated P-384 key to prove the name and lengths follow the key. Explicit-parameter keys are rejected with a clear message.

4. The user types a folder that does not exist and presses Enter. What happens?

Plan assumption 8. The message is cleared by the next key press so the user can simply correct the path.

5. On the "File already exists. Overwrite it?" question the user answers No. What happens?

Esc on the question also means No. Yes overwrites the whole file (it is truncated, not appended) and returns to the menu.

6. Why does the program never draw in the rightmost terminal column?

The fake terminal used in the tests throws if anything writes past that column, so this rule is enforced by tests.

7. Which statement about testing is TRUE?

Section 5 lists these limits. The Windows 11 manual check in that section closes the biggest gap.

8. What is the ScreenBuffer for?

It was not in the original plan sketch; I added it because a rich terminal UI that repaints everything on each key flickers, and the tests need to read back colors.
